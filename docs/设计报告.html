1 项目概述

1.1 背景

学生科技协会的日常运营涉及设备与 3D 打印预约、耗材发放、仪器借还、实验室门禁、元器件库存、活动组织、值班排班、资料归档等十余类事务。实际工作中，这些环节通常分散在微信群、纸质登记表、Excel 表格和多个网盘之间，导致三类问题：

  • 信息不透明：设备是否空闲、耗材还剩多少、门禁谁批准，只能靠人逐个询问。
  • 流程无留痕：借用、审批、发放等关键动作没有统一记录，出现损坏或丢失难以追溯。
  • 交接成本高：负责人换届后，历史数据、权限边界、操作规范都难以完整移交。

本项目把上述业务收敛到一个统一平台，以「一套账号、一套权限、一套数据」覆盖科协运营全流程，并以多种形式对外提供能力：普通成员使用 Web 界面或微信小程序，管理者使用后台完成审批与统计，AI 助手可通过 MCP 工具服务查询运营数据。

  • 权限可配置：管理员按成员职责勾选权限，敏感操作（记账、改设备、看统计）逐接口校验。

  • 数据可追溯：关键写操作写入审计表，备份可下载、可整目录迁移。

3.3 总体方案

系统采用「一个后端、多端接入、按业务垂直拆分」的总体方案：后端以 Express 提供统一的 REST API，鉴权、参数校验、错误处理、审计下沉为公共中间件，业务按设备、库存、门禁、活动、值班、资料、经费、系统八条路由线拆分；Web 前端与微信小程序复用同一套接口，MCP 服务在接口之上做只读封装。由此保证三端看到的权限边界、数据口径与审计记录完全一致。

实现路径按依赖关系推进：先完成账号、权限与审计骨架，再实现设备预约（含冲突检测）、耗材与元器件库存、仪器借还，随后补齐门禁、活动、值班、资料与经费台账，最后完成统计导出、API Key、MCP 工具与容器化部署。每一步都以可运行的接口和测试用例作为完成标准，避免「先堆界面后补逻辑」。

数据库文件位于数据目录下的 classfund.db，开启 WAL 模式以支持读写并发；上传文件存 uploads/，每日备份存 backups/。生产部署将该目录挂载进容器，升级镜像不影响数据。

5 功能设计

5.1 设备预约（含 3D 打印）

成员选择设备、填写时间段与用途提交预约。系统先校验设备状态与时间合法性，再检查该设备是否存在时间重叠的有效预约；重叠则返回 409 并提示冲突时段。需审批设备进入「待审核」，管理员审批通过后方可使用。使用结束由设备管理员标记完成，或由系统按结束时间自动关闭。

冲突判定：两条预约重叠的充要条件是 已有开始 < 新结束 且 已有结束 > 新开始。该判断由数据库执行，避免把全量数据拉到应用层过滤。

5.2 库存与借还

耗材与元器件均采用「台账 + 流水」模型。入库、领用、盘点都写一条流水，台账数量在事务内更新，任何一步失败整体回滚。数量低于预警阈值时在首页与库存页高亮，并在运营总览中计数。

5.3 活动与值班

活动支持草稿、开放、关闭、结束、取消五种状态，报名受截止时间与人数上限双重约束，满员返回明确提示；报名与取消均写审计。值班按班次组织，可指定多人、填写地点与容量，首页展示「今日值班」及「我是否在班」。

5.4 成员与权限

管理员创建成员时指定角色与权限；编辑时按需勾选八项能力。权限判断集中在服务端中间件：请求进入业务逻辑前先解析身份，再比对所需权限键。前端只负责隐藏入口，不作为安全边界。成员被停用或改密时，其已签发令牌通过版本号机制立即失效。

建号提供三种方式：单个新建、按起始账号批量生成、Excel 名单导入。名单导入时系统按「登录账号 → 学号 → 自动分配 kx0001 起账号」的顺序确定用户名，为每人生成符合复杂度要求的随机初始密码并强制首登改密；权限列支持中文写法（如「设备、库存、值班」），服务端解析为权限键。重复账号、缺姓名、权限无法识别等异常逐行跳过并返回行号与原因，导入结果可下载账号表分发，审计日志仅记录账号不记录密码。

5.5 资料与导出

资料按分类归档，上传时校验扩展名与大小上限，下载走鉴权接口而非公开静态目录。导出支持设备台账（全部或按类型）、账单与审计日志，输出 CSV/Excel，中文编码处理避免乱码。

6 关键技术实现

6.1 身份认证与令牌吊销

登录成功后签发 HS256 JWT，有效期 7 天。令牌可经三种方式携带：httpOnly Cookie（网页）、Authorization: Bearer（小程序与 API 调用）、查询参数（文件下载场景）。服务端不维护会话表，但每次鉴权都会读取用户当前状态与 token_version，与令牌载荷比对；改密、重置、停用都会使版本号加一，从而让旧令牌全部失效。首次登录强制修改初始密码。

6.2 登录限流

以「来源 IP + 账号」为键统计失败次数，15 分钟内达到 5 次即拒绝登录并提示稍后再试。计数写入数据库而非内存，进程重启后依然生效，避免攻击者通过重启绕过。成功登录后清除计数。

6.3 API 密钥

管理员或具备 api 权限的成员可签发密钥，明文仅在创建时展示一次，数据库只存 SHA-256 摘要。调用时通过 X-API-Key 或 Authorization: ApiKey 携带；密钥继承持有人权限，且必须满足 api 权限；单密钥按分钟限流，撤销或过期立即失效。

6.4 MCP 工具服务

为满足「以 MCP 工具服务形式交付」的要求，项目在不引入额外依赖的前提下实现了一个 MCP stdio 服务，通过 JSON-RPC 处理 initialize、tools/list、tools/call，将设备、库存、耗材、活动、预约、运营总览、资料检索七类查询封装为工具。工具内部复用 REST API 与 API Key 鉴权，因此无需在 MCP 层重复实现权限体系；所有工具均为只读，写操作仍回到 Web 界面，降低 Agent 误操作风险。

6.5 容器化与进程协作

镜像采用多阶段构建：先构建前端产物，再安装服务端生产依赖，最终镜像同时包含静态资源与 API 服务。Compose 定义应用、worker、Nginx 三个服务，应用与 worker 共享数据卷，Nginx 依赖应用健康检查通过后启动，从而避免「容器起来了但接口未就绪」。

8 部署与运维

8.1 部署结构

  • 宿主机安装 Docker 与 Compose，项目目录包含 docker-compose.yml 与数据目录。
  • 应用容器监听内部端口，仅由 Nginx 容器访问；Nginx 对外暴露单一端口。
  • 如需 HTTPS，由宿主机 Nginx 或云负载均衡终止 TLS 后转发至容器端口。
  • 支持 NAS 部署：本地磁盘目录挂载数据卷，避免使用网络文件系统（SQLite 依赖文件锁）。

8.2 升级与备份

  • 升级：拉取代码后执行 docker compose up -d --build，数据卷不受影响。
  • 备份：worker 每日生成备份包并保留最近 14 天，管理员可一键立即备份并下载。
  • 恢复：停止服务，替换数据目录，重启即可；数据库与上传文件同目录，保证一致性。
  • 可观测：管理员「运行状态」展示版本、运行时长、内存、数据库体积、worker 在线状态与最近备份时间。

8.4 评测环境可用性说明（HTTPS 与微信小程序）

HTTPS：域名 astmgr.icu 的 Let's Encrypt 证书已签发（有效期至 2027-02），宿主机 Nginx 443 已配置 TLS 与 HTTP 跳转。因 ICP 备案在提交截止前来不及完成，域名链路在访问时被拦截，评测环境临时改用 http://1.14.125.216/ 直连。此模式下口令与令牌在链路上未加密，仅用于评测；备案完成后改回域名并将 COOKIE_SECURE 置为 1 即可恢复全加密，代码无需改动。
微信小程序：因同样的备案原因无法配置 request 合法域名，且小程序未提交发布，本次评测暂不可用。小程序源码（Taro + React + TS）与 H5 预览完整保留在 miniapp/，复用同一套 REST API 与 Bearer 鉴权；备案完成后修改 miniapp/src/config.ts 中的 API_BASE_URL 为 HTTPS 域名即可启用，服务端无需改动。

10 创新点与展望

10.1 创新点

  • 一平台多形态：同一套后端同时服务 Web、小程序与 MCP 工具，权限与审计口径统一。
  • 权限可配置而非角色堆叠：两角色 + 八权限的组合，比传统「财务员/技术员/管理员」更贴合社团人员流动。
  • 零外部依赖的持久化方案：内置 SQLite + 单文件备份，让社团无需数据库运维能力也能长期运行。
  • 可解释的安全设计：令牌吊销、限流、密钥摘要等机制均有明确的威胁对应关系，便于评审与交接。

10.2 不足与改进方向

  • 目前为单机单实例，无高可用；后续可引入对象存储做异地备份，并增加监控告警。
  • 未接入统一身份认证（学校 SSO）与双因素认证，可作为下一阶段安全增强。
  • MCP 工具当前只读，后续可在审批场景引入「人工确认后执行」的写操作工具。
  • 小程序端可继续补充扫码借还、消息订阅提醒等移动端特性。
